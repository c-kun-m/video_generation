# G04｜持久化编排、取消与恢复

> 状态：DRAFT_FOR_REVIEW。交付阶段：B1。前置：G01–G03、G09/G10 的模拟端口。下游：G05、G07、G10、G11、G13。

## 1. 目标与边界

让每一次创作任务和制作批次都有可恢复的执行过程。Temporal 决定何时调用下一步和等待什么，不绕过领域服务修改项目内容。网络、LLM、数据库、ComfyUI 等外部操作放在 Activity 中，Workflow 只处理确定性的编排逻辑。

## 2. 功能清单

| ID | 功能 | 输入与输出 | 交互对象 | 实现要点 |
|---|---|---|---|---|
| G04-F01 | 创作短工作流 | creative_task_id → 草稿结果引用 | G05、G07 | 一次需求整理/剧本/分镜/配音任务一个实例 |
| G04-F02 | 制作工作流 | production_run_id/snapshot_ref → 制作结果 | G08–G13 | 分阶段汇合、等待审片、按冻结合成版本执行 |
| G04-F03 | 重试与超时 | 分类错误 → 重试/暂停/失败 | G09、G10 | 明确 Activity 的副作用身份和时间界限 |
| G04-F04 | 暂停、恢复、取消 | 已持久化命令 → 可观察执行状态 | G03、G10、G14 | 暂停不新增任务；取消等待外部执行确认 |
| G04-F05 | 崩溃恢复与状态对账 | Workflow 历史/业务记录 → 修复动作 | G03、G16 | 重放不重复已记录结果；未知外部结果先回查 |
| G04-F06 | 工作流版本治理 | 新代码 → 新执行版本 | G16、G17 | 活跃实例固定兼容代码；历史回放和升级演练 |

## 3. 工作流划分与流程

`CreativeTaskWorkflow` 的 ID 为 `creative/<tenant>/<creative_task_id>`；`ProductionWorkflow` 的 ID 为 `production/<tenant>/<production_run_id>`。业务 Run ID 不随 Temporal Continue-As-New 改变，Temporal run_id 只用于追踪内部执行链。应用级幂等键不取会改变的 Temporal run_id。

创作流程：LoadTask → AdmitBudget → ExecuteCreativeOperation → ValidateResult → SaveDraftRevision → SetTaskResult。人修改草稿和批准版本由 G03 管理，不让一个项目终生绑定一个巨大的 Agent 循环。

制作流程：LoadSnapshot → VerifyInputs → AdmitBudget → EnsureRenderJobs → WaitForJobs → TechnicalQC → WaitForSelection → ValidateCompositionRevision → Compose → WaitForFinalApproval → RegisterExport → Complete。

`EnsureRenderJobs` 使用快照中固定的候选槽 ID 创建逻辑任务，重复 Activity 返回同一批 job_id。用户要求新候选或修改镜头时经 G12 创建新操作，不能靠“重试 EnsureRenderJobs”偷偷增加候选。

候选结果、审批和选片通过事件唤醒流程。Activity 从业务数据库读取已持久化事实并验证快照归属；唤醒通知可重复，状态转换不重复。工作流等待期间不占用 GPU 租约或数据库连接。

## 4. Activity 合同

| Activity 类别 | 输入身份 | 自动重试策略 | 成功证据 |
|---|---|---|---|
| 只读校验/查询 | 业务对象引用 | 最多 5 次，指数退避 | 验证结果和引用摘要 |
| 数据库状态转换 | operation_id + expected_version | 短事务重试；已应用返回原结果 | 事务记录/事件 ID |
| LLM/TTS 调用 | creative_task_id + operation_id | 供应商去重/回查支持决定；未知结果暂停 | 已保存输出引用和调用记录 |
| GPU 提交 | job_id + attempt_id | G10 控制提交；未知结果禁止直接重提 | Worker 持久化回执和外部关联 |
| 查询/收集 GPU 结果 | job_id + attempt_id | 可重试查询/上传；不得重新生成 | READY artifact + Manifest |
| 合成 | composition_ref + media_job_id | G13 的本地任务去重和产物回查 | 校验通过的合成文件引用 |

每个 Activity 必须配置最大执行时间；轮询型任务按配置轮询间隔运行，或采用异步完成适配。初始建议：普通数据库操作 10 秒、模型请求 120 秒、结果查询 30 秒；真实 GPU 超时来自 G08 的实测 profile，不能统一写死 30 秒。这些值属于可观测的版本化运行配置，验收后调整。

Temporal 可能重新执行尚未成功登记结果的 Activity，外部幂等需要接收端实现；将操作放进 Activity 不会自动使 GPU 或 LLM 调用只发生一次。[Activity 官方说明](https://docs.temporal.io/activity-definition)

## 5. 暂停与取消语义

暂停：领域记录 pause_requested，Workflow 停止新增生成/合成任务，已经运行的任务继续收集结果；直到安全检查点进入 PAUSED。恢复继续使用相同快照和已经完成的结果。需要立即停止资源消耗时使用取消。

取消：先持久化 CANCEL_REQUESTED → 调度层禁止新领取 → 删除尚未提交的队列项 → 对已运行任务执行 G10 的定向中止/实例隔离 → 收集最终执行事实 → 确认没有仍会继续执行的工作后进入 CANCELLED。取消竞态中到达的文件可登记为取消后的孤立候选，不能自动被选中或触发合成。

外部节点失联且无法确认停止时保留 CANCEL_REQUESTED，并显示未确认的 attempt；不能为了让状态好看直接标记 CANCELLED。运维确认隔离实例后可以结束取消，但须留下执行证据和费用结算记录。

工作流正常取消采用能继续执行必要清理的专用 Activity/取消屏蔽作用域；不使用 Temporal Terminate 作为日常取消按钮。Terminate 仅用于有审计的运维处置，随后必须由 G16 对账遗留任务。

## 6. 重启、历史与升级

服务重启后，Temporal 从已持久化历史恢复编排；数据库状态投影通过幂等领域操作修复。Outbox 定期检查 CREATED 但尚无工作流确认的 Run，按稳定 ID 补启动。后台检查“数据库显示运行但 Workflow 已结束/不存在”等不一致，生成告警和可审计修复任务。

Workflow 历史只保存引用、小结果和关键业务通知；禁止写入视频帧、逐 token 输出或高频 GPU 进度。等待审片超过 7 天发产品提醒标记；30 天默认暂停待用户恢复，不自动批准、删除素材或继续花费预算。

历史接近限制时使用 Continue-As-New，携带业务 Run ID、阶段、待消费事件标识和当前引用，并等待处理中的消息完成。该机制会更新 Temporal run_id，因此业务身份必须独立。[Continue-As-New 说明](https://docs.temporal.io/develop/typescript/workflows/continue-as-new)

生产部署使用验证过的 Worker Versioning/Pinning 配置；旧活跃流程继续由对应版本处理，新流程逐步切换。所用 Server/SDK 必须满足该功能的兼容要求，由 G01 锁定。[Worker Versioning 说明](https://docs.temporal.io/production-deployment/worker-deployments/worker-versioning)

## 7. 实现任务

先用模拟端口实现两个 Workflow 和每阶段产物引用；再接 Command/Outbox；随后建立取消/恢复和错误分类；最后接真实供应商。Workflow 测试使用虚拟时间覆盖长期等待，集成测试用真实持久化服务注入进程故障。业务状态与编排状态不一致时必须通过领域命令修复，不用人工编辑 Temporal 内部数据库。

## 8. 验收条件

- G04-A1：在每个主要阶段终止并重启 Worker，已登记成功的步骤不重新产生候选，未完成步骤按分类恢复。
- G04-A2：Activity 写业务成功但结果回报丢失，重执行返回原业务结果，没有重复版本或重复任务。
- G04-A3：暂停期间在途任务可完成，但没有新 GPU 提交；恢复后复用其结果。
- G04-A4：取消与成功同时到达时，没有自动选片/合成；失联外部执行保持取消未确认。
- G04-A5：审批事件重复/乱序/跨 Continue-As-New 到达，不重复消费且不批准错误版本。
- G04-A6：新版本上线后旧历史回放通过，至少一个旧活跃实例由旧部署继续完成。

## 9. 供审核的取舍

首版就使用 Temporal，接受一项独立基础设施的运维成本，换取长流程恢复的明确实现路径。它不代替任务数据库、外部回查和业务幂等。不再叠加 Celery 或 LangGraph 作为第二个全局编排器。
