# G02｜领域协议、版本与数据存储

> 状态：DRAFT_FOR_REVIEW。交付阶段：B0。前置：G00、G01。下游：G03–G14；所有权受 G15 约束。

## 1. 目标与边界

把“用户想制作什么”“系统执行了什么”“实际生成了哪个文件”分开存储。每次已批准内容和生产输入均可准确定位，修改不会覆盖历史。Schema 是结构合同，数据库约束负责并发和关系正确性，不能仅依赖前端校验。

Python 实现采用 Pydantic v2 作为结构合同的唯一编写入口，按版本生成 JSON Schema 2020-12 和 OpenAPI，存入根目录 `contracts/`；前端 TypeScript 类型/客户端从发布合同生成。旧合同版本保留读取能力，重新生成不得覆盖已发布版本。严格字段与未知字段校验、输入/输出序列化及共同有效/无效样例在 B0 验证，Python 自定义校验中的领域规则也要有明确错误合同，不能误称都已表达进 JSON Schema。

## 4. 内容合同与执行合同

镜头只描述创作目标；工作流编译器决定具体实现。

```json
{
  "schema_version": "shot-spec/v1",
  "shot_id": "shot_03",
  "revision": 2,
  "intent": "人物背对镜头，摄影机缓慢靠近",
  "duration_frames": 120,
  "fps": {"num": 24, "den": 1},
  "camera": {"size": "medium", "movement": "slow_push_in"},
  "reference_refs": [{"asset_id": "character_a", "revision": 1}],
  "continuity_refs": []
}
```

```json
{
  "schema_version": "render-spec/v1",
  "render_spec_id": "rs_03_01",
  "shot_ref": {"shot_id": "shot_03", "revision": 2},
  "workflow_bundle_digest": "sha256:EXAMPLE",
  "compiler_version": "compiler-v1",
  "resolved_inputs": {"positive_prompt": "...", "seed": 12345},
  "native_media_profile_ref": "profile_registered_01",
  "input_artifacts": [{"artifact_id": "reference_01", "digest": "sha256:EXAMPLE"}],
  "execution_digest": "sha256:EXAMPLE"
}
```

示例 ID/摘要是占位值，不是可执行测试素材。真实 RenderSpec 必须展开模型支持的宽高、帧数、fps、采样器等字段；可选参数按工作流能力校验。种子由编译阶段具体化，不允许提交时使用“随机/自增”占位。

所有引用由服务端验证同项目或明确允许的同租户共享素材权限。租户身份不由上述 JSON 提供。整数帧、时长和字节数均有上限，拒绝 NaN/Infinity、负时长、重复镜头槽和循环引用。

公共引用类型统一为：ShotRef 使用 shot_id/revision；AssetRef 使用 asset_id/revision；ArtifactRef 使用 artifact_id/digest；TimelineRef 使用 timeline_id/revision。持久化时对应 digest 必须可解析且固定。跨对象通用接口使用带 kind 的 SubjectRef，并在 Schema 中映射到上述具体类型，不混用未说明的 `id` 字段。

## 5. 版本、摘要与并发规则

1. 编辑内容时带 expected_row_version。事务锁定当前头，比较序号，插入新版本、更新头指针、写事件；冲突返回 409 和当前版本，不能后写覆盖先写。
2. 已保存 Revision 不原地改写，包括提示词、审批目标和引用资产。新版本可以继承旧版本字段，但要保存完整可读取内容及父引用。
3. 对采用固定规范的 JSON 做 canonical serialization 后计算 SHA-256；明确键排序、数组顺序、数值表示、空值语义。摘要算法和规范版本写入合同，并用跨进程固定样例验证。
4. `execution_digest` 只覆盖实际执行输入和环境/编译器摘要；不混入项目展示标题、project_revision、job_id 等无关身份。这样无关修改不会破坏复用。缓存查找仍必须验证租户权限及 G12 的复用策略。
5. job_id/candidate_id 是操作身份，不用 execution_digest 代替。相同执行输入允许用户创建多个候选，缓存不能吞掉主动新生成。
6. `ProductionSnapshot` 冻结创作输入及计划；生成结果由后续 SelectionRevision、CompositionRevision 引用，避免试图把尚未生成的 artifact_id 填进初始快照。

## 6. 状态合同与写入责任

| 状态对象 | 合法状态 | 写入入口 |
|---|---|---|
| 内容审批 | DRAFT / APPROVED / REJECTED / REVOKED（针对具体版本） | G03；显示状态从审批记录计算 |
| ProductionRun | CREATED / PREPARING / RENDERING / REVIEW_REQUIRED / COMPOSING / COMPLETED / PAUSED / FAILED / CANCEL_REQUESTED / CANCELLED | G04 调用领域状态转换，附 expected_row_version 和原因 |
| RenderJob | CREATED / QUEUED / DISPATCHED / RUNNING / SUCCEEDED / FAILED / OUTCOME_UNKNOWN / CANCEL_REQUESTED / CANCELLED | G09/G10 的唯一状态转换函数 |
| RenderAttempt | ALLOCATED / SUBMITTING / ACCEPTED / RUNNING / COLLECTING / SUCCEEDED / FAILED / OUTCOME_UNKNOWN / CANCELLED | G10 带 fence 提交执行事实 |
| Artifact | UPLOADING / READY / QUARANTINED / DELETE_PENDING / DELETED | G06；未 READY 禁止被选片和合成使用 |

PAUSED 表示暂停安排新工作，不表示 GPU 能从任意采样中间点暂停。失败尝试允许保留部分输出，但不等于逻辑任务成功。ProductionRun.COMPLETED 指已完成本次交付审批与登记，不等于所有历史任务均成功。

ProductionRun.stage 区分 PREPARE_INPUTS、RENDER_SHOTS、REVIEW_SELECTION、COMPOSE、REVIEW_FINAL、EXPORT；同样是 REVIEW_REQUIRED 时，用 stage/waiting_subject_ref 指明等待哪一次选片或成片审批。暂停保存原阶段和待处理引用，恢复时重新检查预算及依赖，不从头生成。

RenderJob 状态转换必须编码为白名单，至少覆盖：

| 转换 | 允许条件 |
|---|---|
| CREATED → QUEUED | 依赖就绪、预算准入成功 |
| QUEUED → DISPATCHED → RUNNING | 合法领取，以及对应外部受理/执行证据 |
| DISPATCHED/RUNNING → SUCCEEDED | 对应结果已收集为 READY Artifact，允许没有收到完整进度事件 |
| DISPATCHED/RUNNING → QUEUED | 旧 Attempt 已知失败/未提交/确认停止，策略允许技术重试；必须新建 Attempt |
| DISPATCHED/RUNNING → OUTCOME_UNKNOWN | 提交/执行事实无法确认，保留实例和尝试关联 |
| OUTCOME_UNKNOWN → RUNNING/SUCCEEDED | 回查确认仍在执行或已经产生有效结果 |
| OUTCOME_UNKNOWN → QUEUED/FAILED | 获得明确未执行/已停止证据并满足重试策略，或人工作出有审计的处理 |
| 非终态 → CANCEL_REQUESTED → CANCELLED | 已持久化取消意图，并确认该任务不会继续执行 |
| CREATED/QUEUED/DISPATCHED/RUNNING → FAILED | 明确不可恢复错误或尝试上限耗尽；未知结果不能直接归类已知失败 |

SUCCEEDED/FAILED/CANCELLED 为逻辑任务终态，不接收晚结果改写；后续要求重新生成创建新 Job。Attempt 失败不必导致 Job 终态失败，二者由上述重试规则连接。Run 取消时已经 SUCCEEDED 的子任务保持成功历史，未被选用结果不会自动触发合成。

PostgreSQL 是业务事实的读取依据。Temporal 历史是执行编排记录，不供 UI 直接编辑；UI 从业务 API 获得快照。模块写状态时校验状态迁移、版本、租户和执行世代，不允许任意 SQL 更新 status。

## 7. 数据库实施与失败处理

- 所有租户域表主键/唯一键至少提供 `(tenant_id, id)` 约束；关联使用同租户复合外键。Revision 以 `(tenant_id, entity_id, revision)` 唯一。
- Python 仓储采用 SQLAlchemy 2 + psycopg 3，数据库迁移采用经审查的 Alembic revision。不同并发请求/任务不共享 AsyncSession；自动生成迁移需核对复合外键、唯一约束和索引，不能在运行启动时用建表操作替代迁移。
- 单聚合修改采用事务和行锁/版本比较；跨聚合业务操作固定加锁顺序，避免死锁。数据库序列化失败可重试尚未产生外部副作用的事务，不把重试扩展到 GPU/LLM 调用。
- 业务事件与变更同事务提交。外部文件上传和任务调用不在数据库事务内长时间等待，使用 G06 的上传确认与 G03 的 Outbox。
- 迁移先新增兼容字段，再迁移数据，再切读路径；旧数据 Schema 保留读取适配。备份验证与破坏性收缩按 G16。
- 索引覆盖项目列表、任务状态与 next_attempt_at、Outbox 未投递项、输入反向依赖、同租户素材引用；上线前用实际查询计划验收。

事务隔离不能替代业务上的版本校验，具体并发测试应覆盖 PostgreSQL 所选隔离级别。[PostgreSQL 事务隔离说明](https://www.postgresql.org/docs/17/transaction-iso.html)

## 8. 实现任务与验收

实现顺序：Schema 与固定样例 → migrations/约束 → 版本仓储 → 状态转换函数 → 快照构建器 → 依赖边写入 → 并发及迁移验收。

- G02-A1：两个客户端同时改同一镜头，仅一个基于原版本的写入成功；另一个收到可恢复的冲突，旧版本不变。
- G02-A2：审批分镜 v3 后生成 v4，v4 不继承 v3 的批准；已有制作快照仍指向 v3。
- G02-A3：修改项目标题不改变镜头 execution_digest；改变角色参考或工作流摘要会改变摘要。
- G02-A4：数据库拒绝跨租户外键和重复 revision；普通列表/查询不泄露其他租户对象。
- G02-A5：同输入创建两个 candidate_id，产生两个逻辑任务；重试同 command_id 只返回原逻辑任务。
- G02-A6：文件尚未 READY 或引用 Schema 不兼容时，冻结快照/选片失败且返回字段级原因。

## 9. 供审核的取舍

版本化数据比直接覆盖字段占用更多存储，但能支持审查和局部重做。采用独立 ProductionSnapshot、SelectionRevision、CompositionRevision，避免“整个项目只有一个 version”的混淆。首版不实现任意版本自动合并；冲突由用户比较后重新提交。
