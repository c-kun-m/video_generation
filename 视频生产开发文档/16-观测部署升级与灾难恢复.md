# G16｜观测、部署、升级与灾难恢复

> 状态：DRAFT_FOR_REVIEW。交付阶段：B0 基础日志/部署，B4 完整运维验收。前置：G01；与 G02–G15 各模块配合。下游：G17 发布门禁。

## 1. 目标与边界

系统能回答任务卡在哪里、是否仍在消耗资源、产物能否找回，以及升级失败后如何恢复。进程重启恢复和整机/存储灾难恢复分别设计，不把 Temporal 的工作流恢复能力扩展为“所有文件和数据库永不丢失”的承诺。

## 3. 观测合同

结构化日志共同字段：timestamp、severity、service/build、tenant/project（按权限脱敏）、command_id、creative_task_id/production_run_id、job_id/attempt_id、workflow_id/temporal_run_id、worker/instance_epoch、artifact_id、trace_id、error_code。没有的字段省略，不能造 ID 串链。

G03 的 command_id 与业务事件关联；G04 的 Activity 记录 operation_id；G10 保存本地回执引用；G13 保存媒体执行日志。跨进程传播上下文，日志可以通过 trace_id 查到关联记录。高频进度进行采样/限速，业务状态事件仍可靠保存。

最低指标：各阶段耗时/成功率、Outbox 最老未送达时间、CREATED 未启动 Run 数、队列等待时间、节点接单数/失联数、OUTCOME_UNKNOWN 数、取消未确认时长、上传失败、磁盘/对象存储占用、LLM Token、GPU 秒、预估与实际成本偏差、人工驳回率。

初始告警：Outbox 超过 60 秒未送达、Worker 超出租约未心跳、未知结果超过 10 分钟未处理、关键存储空间低于 15%、实际费用超预留。阈值是待压测校准的配置，不是商业 SLA；规则要避免把正常长生成误报为故障。

## 4. 部署拓扑与启动顺序

本机开发可采用独立服务栈：PostgreSQL（业务/Temporal 使用分开的数据库和身份）、Temporal 服务、Video API、Workflow Worker、对象存储/文件开发后端、Render Worker+ComfyUI、Media Worker。数据库和执行日志明确挂载持久卷；Docker Compose 只是部署入口，不代表已经实现高可用。

Windows 桌面不拥有该服务栈。若 ComfyUI 在 Windows 原生环境运行而服务栈在容器/另一台机器，按网络可达性配置 Worker 出站连接与受控素材传输，不共享隐含的 `C:\...` 路径。没有后台主机可用时任务暂停，不能靠 UI 在线状态伪装执行。

启动：校验配置/版本 → 数据迁移 → 存储/数据库健康 → Temporal 就绪 → API/Outbox → Workflow Worker → Render/Media Worker 对账 → 开放领取。停止：关闭新命令准入 → 停止新领取 → 排空或保留未决日志 → 关闭服务。强制停止留待恢复检查，不把未决任务删除。

每个部署产出 Release Manifest：Git 提交、所有依赖/制品摘要、Schema 版本、数据库迁移版本、Temporal Worker build、Bundle 摘要、FFmpeg/font profile、配置版本及测试证据引用。秘密只通过运行时注入，清单保存秘密名称而非值。

Python 业务制品记录解释器版本、uv 锁文件、FastAPI/LangChain/temporalio 依赖与 Alembic revision；前端记录 Node/pnpm 和独立锁文件；ComfyUI 记录自己的 Python/PyTorch/CUDA/节点闭包。三个环境分别构建并持久化各自运行数据，不把业务依赖安装到 ComfyUI 环境中。

## 5. 升级与回退

先在隔离环境恢复一份脱敏/测试数据，运行迁移和工作流历史回放；再部署新版本到受控环境。API 兼容旧客户端至少一个已发布合同主版本的协商范围，遇到不兼容返回明确升级要求。

活跃 Temporal 流程固定兼容 Worker 版本，保留处理旧流程所需代码。Bundle 升级不覆盖旧模型/节点闭包。数据库采用扩展、迁移、切换读取、最后收缩的顺序；不可逆 schema 变更不能承诺只回退二进制就恢复。

失败回退优先恢复旧应用/Worker 路由，仍允许新加的兼容字段留存。若涉及不可逆数据变更，进入恢复方案并说明恢复点；禁止在生产数据上反复尝试未经验证的 down migration。

## 6. 备份与恢复演练

业务数据库采用基础备份与持续日志归档/等价的经验证方案；Temporal 持久化按选定部署模式执行对应备份策略；对象存储保留固定对象版本或不可覆盖键；Worker journal、未上传输出和模型/工作流包也纳入保留计划。

备份保存恢复清单：业务数据库位置/时间、Temporal 数据位置/时间、素材对象版本与引用、工作流和应用代码版本、Worker 未决日志范围。两个数据库与对象存储不假装有天然一致快照；恢复时对账缺口，必要时进入受控降级。

恢复步骤：隔离旧执行节点 → 在新环境恢复数据与素材 → 禁止所有新 GPU/LLM 派发 → 校验引用和对象摘要 → 对账数据库/Temporal/Worker/供应商状态 → 未确认任务进入 OUTCOME_UNKNOWN → 人工审查恢复报告 → 开放新任务。

数据库恢复到较早时间可能忘记恢复点后的外部执行；这时重新运行具有重复副作用风险。必须使用独立保留的 Worker 日志/供应商记录补证据，证据缺失则保留未知，不自动重新派发。旧系统未隔离前不能同时开放新系统领取。

初始恢复目标建议：数据库灾难恢复 RPO 不超过 15 分钟、完整服务 RTO 不超过 4 小时；RPO 是允许的数据恢复点差距，RTO 是允许的恢复耗时。它们是 B4 待演练验证的目标，未测得前不能对用户承诺。已经批准交付的对象应有至少一份经过校验的备份，未上传 Worker 输出的风险单独记录。

## 7. 容量与实现任务

API/事件/媒体流/日志均设置有界缓冲；磁盘不足先停止准入，再收集已有任务，不删已选文件腾空间。监测队列等待与模型加载开销后决定增加 Worker，而非先引入 Kubernetes。

实现顺序：统一日志字段和错误码 → 独立部署与持久卷 → 健康探测/基本指标 → Outbox/任务对账 → 版本 Manifest → 升级回放 → 备份恢复脚本及演练 → 容量阈值校准。命令和脚本在实施时提供可复制运行说明，本稿不把尚不存在的脚本当成交付物。

## 8. 验收条件

- G16-A1：给定一个失败 job_id，可定位命令、快照、Attempt、ComfyUI 回执、输出和成本记录，日志无测试秘密。
- G16-A2：API/Worker 重启后持久数据仍在；正常停止和强制停止均有可解释恢复结果。
- G16-A3：新应用/工作流/Bundle 上线后，旧活跃任务仍按固定输入完成；回退演练有证据。
- G16-A4：在隔离环境恢复备份并实际播放已交付视频，不只验证备份命令返回成功。
- G16-A5：恢复点后可能已执行的任务被识别为待对账，不立即产生重复 GPU 提交；旧节点被隔离。
- G16-A6：空间不足、Outbox 堆积和长期未知任务触发有效告警与准入限制。
- G16-A7：记录实测 RPO/RTO、备份覆盖范围和未满足项；未达到目标不能宣称通过 B4。

## 9. 供审核的取舍

先部署独立服务栈与少量 Worker，保留扩容接口；高可用、多区域和自动伸缩另行评估。备份恢复、工作流升级和未知任务对账属于对外发布前必须验证的能力。
