## 4. 每个目标的完成证据

实施阶段创建 `evidence/features/<feature-id>.json`（此处为未来路径），至少包括 design_revision、status、implementation_commit/paths、contract_test_refs、failure_test_refs、manual_review、known_limits、release_manifest_ref。

状态为 DRAFT → DESIGN_APPROVED → IMPLEMENTING → VERIFIED → RELEASED；有问题时记 CHANGES_REQUIRED 或 BLOCKED 并写原因。现有文档功能均为 DRAFT，验收项均未运行。单个目标 VERIFIED 必须覆盖其所有首版功能和目标文件里的验收 ID。

G17-F01 由校验脚本扫描每个文件功能表生成索引，检测重复 ID、失效链接、漏写验收和未追踪的实现变更。实现/测试证据以内容摘要和提交关联，避免文件换了但旧报告仍显示通过。

## 5. 故障注入矩阵

| 编号 | 注入位置 | 必须观察到的结果 | 主要责任 |
|---|---|---|---|
| E01 | 同一命令并发提交 20 次 | 一个业务操作；新候选命令则可以产生新任务 | G03、G09 |
| E02 | 数据库提交后、HTTP 返回前杀 API | 查询原 command_id 找回结果，不重新创建 Run | G03 |
| E03 | Outbox 发送后、标记送达前杀投递器 | 重发收敛为同一工作流/业务消费 | G03、G04 |
| E04 | 批准 v3 后提交 v4 制作 | v4 必须重新批准；v3 记录不变 | G02、G03 |
| E05 | ComfyUI 受理后、回执落盘前断网 | 找回或 OUTCOME_UNKNOWN，不盲目再次提交 | G10 |
| E06 | 清空 ComfyUI 历史并换实例世代 | 查不到不能当成未执行；旧映射不关联新实例 | G10 |
| E07 | GPU 成功后，上传/数据库登记失败 | 只补收集/登记，GPU 提交次数不增加 | G06、G10 |
| E08 | Worker 租约过期后恢复晚报 | 旧 fence 不覆盖当前结果，也不自动重复计算 | G09、G10 |
| E09 | 取消与完成同时发生 | 取消状态有证据；没有自动选片/合成 | G04、G10、G11 |
| E10 | 暂停时有在途任务 | 在途结果可收集，无新任务被派发 | G04、G09 |
| E11 | ImpactPlan 生成后修改内容/价格 | 提交检测过期或超限，不静默扩大重做范围 | G03、G12 |
| E12 | 多任务竞争最后预算额度 | 原子预留，不重复扣父子额度；未知费用不提前退还 | G09 |
| E13 | 旧结果晚于用户新选片到达 | 旧结果可查询，新选择不被覆盖 | G02、G11、G12 |
| E14 | FFmpeg 成功后上传失败/进程取消 | 补上传不重算；取消不误杀其他任务 | G13 |
| E15 | 数据恢复点早于外部执行 | 先隔离/对账，再开放任务；不自动重复执行 | G16 |
| E16 | 跨租户猜 ID、撤销会话/Worker | API、事件、素材、血缘和内部接口授权正确 | G15 |

测试应记录可直接验证的外部提交次数、逻辑任务数、预算账本和文件摘要；不能只断言内部函数被调用了几次。模拟器必须支持可控故障，真实 ComfyUI 至少复核受理/回查/取消/输出格式契约。

Python 后端采用 pytest 和 Temporal Python 测试工具验证上述合同与故障，Ruff 执行静态检查；前端采用 Vitest/Playwright。另用共同有效/无效样例检查 Pydantic、版本化 JSON Schema/OpenAPI、生成的前端客户端与 Temporal JSON 序列化一致，防止改用 Python 后发生跨语言协议漂移。

## 6. 真实业务验收样例

固定用例集采用三个经审核需求：一个无人物解说、一个固定角色参考、一个含字幕/音乐的产品说明。每例保存输入文本、音频/参考图、模型和 Bundle 版本。首版完整演示以 30 秒、6 镜头、24 fps、720×1280 为基准。

至少完成人工评审：旁白是否完整、字幕是否同步且可读、动作是否表达正确、人物/场景是否明显突变、镜头衔接是否合理、最终成片是否符合需求。允许生成多个候选后选择，但要记录总调用次数、时间与成本，不能只展示挑选后的最佳结果而隐藏过程成本。

必做修改：只改字幕、只换音乐、改一个镜头动作、换角色参考、改旁白长度。分别验证实际调用范围与 G12 影响清单一致。

## 7. 容量、升级与恢复门槛

性能报告必须记录测试机/数据库/存储/网络配置、版本和负载。初始控制面目标：10 个并发客户端、50 个活动制作批次的模拟状态负载下，非媒体流 API p95 小于 500 ms、业务状态变化到 UI 可见 p95 小于 2 秒。它们是 B4 待验证目标，不是对任意用户机器的承诺，真实 GPU 时长独立测量。

至少一次 24 小时有界负载运行，内存、日志、临时空间没有随任务完成持续无界增长；两租户/两实例验证配额和隔离。生成质量和吞吐按真实模型报告，不用模拟器耗时代替。

升级验收包含旧工作流继续执行、旧客户端合同协商、新旧 Bundle 同时引用及数据库迁移后回退；灾难恢复按 G16 验证 RPO/RTO 并实际播放恢复的成片。

## 10. 发布判断

本稿交付的是待审核设计，不是已实现系统。用户批准设计后才进入相应开发范围；开发过程中可以完成可逆实现和验证，实际部署、对外发布等动作仍按当时的用户授权执行。任何首版必需验收未完成，都应保留未完成状态和具体原因。
