# G10｜ComfyUI 执行与不确定结果处理

> 状态：DRAFT_FOR_REVIEW。交付阶段：B1 模拟器，B2 真实执行。前置：G02–G04、G06、G08、G09。交互：G11、G15–G17。

## 1. 目标与边界

将冻结的 RenderSpec 提交到指定 ComfyUI 实例，可靠收集产物。尤其处理“已经提交，但还没保存回执就断网/崩溃”的窗口。目标是明确业务去重和恢复行为；在外部系统无法证明执行结果时，不作“物理 GPU 永远只运行一次”的无条件承诺。

## 2. 功能清单

| ID | 功能 | 输入与输出 | 交互对象 | 实现要点 |
|---|---|---|---|---|
| G10-F01 | 执行环境预检 | Lease + RenderSpec → 可执行/配置失败 | G08、G09 | 验证模型/节点摘要、素材和磁盘、实例归属 |
| G10-F02 | 持久化提交与任务映射 | Attempt → 本地日志/外部回执 | G09、G04 | 提交前记账，提交后绑定实例世代与 prompt_id |
| G10-F03 | 未知结果回查 | 断线/重启 → 找回/未执行/未知 | G04、G09、G16 | 不能只查不到历史就断言从未执行 |
| G10-F04 | 进度与产物收集 | WS/历史/输出 → 遥测 + READY Artifact | G06、G11、G14 | WS 用于提示，成功由输出校验和登记确定 |
| G10-F05 | 定向取消与实例隔离 | cancel 请求 → 已停止/未确认 | G04、G09 | 验证当前任务身份后才允许中止实例 |
| G10-F06 | Worker 重启与遗留任务处理 | 本地日志 + 控制面记录 → 对账 | G09、G16 | 重启先隔离检查，完成对账后再开放领取 |

## 3. 适配器本地持久化

每个 Render Worker 使用持久卷保存 execution journal（建议 SQLite WAL + 明确同步配置，具体模式经断电/进程故障测试），ComfyUI output 与输入缓存分别有独立目录。容器临时文件系统不能承担唯一回执存储。

日志键为 attempt_id，内容包含 job_id、candidate_id、worker_id/epoch、lease_fence、comfy_instance_id/epoch、render_spec_digest、request_digest、state、request_marker、prompt_id（可空）、本地输出路径集合、上报确认位置和时间。日志不得保存供应商秘密。

`prompt_id` 与 ComfyUI 实例身份和世代一起使用；单独一个 prompt_id 不能作为全局唯一执行身份。重启/替换实例必须生成新 instance_epoch，旧日志不能误关联到新实例。

## 4. 提交算法

1. 收到 Lease 后先校验当前 fence、实例空闲及 Bundle 实际摘要；重复收到同 attempt_id 时查本地日志，不直接提交第二次。
2. 下载/验证输入素材，生成本次受限目录和唯一输出前缀。根据已锁定 bindings 编译 API Format 请求；记录完整 request_digest。
3. 持久化 PREPARED 日志，再持久化 SUBMITTING 标记，随后执行一次 POST `/prompt`。
4. 收到成功回执后，先落盘保存 prompt_id/实例关联，再向控制面提交 ACCEPTED 事件；控制面重复事件按 event_id 去重。
5. 如果在 POST 前可以证明未进入提交阶段，允许安全重试；进入 SUBMITTING 后发生超时、响应解析失败或崩溃，按结果未知处理。

“PREPARED/SUBMITTING”是本地日志状态，对外映射到 G02 的 ALLOCATED/SUBMITTING。数据库与本地日志不假装具有一个原子事务，重复上报和对账负责收敛。

ComfyUI 提供 POST `/prompt`、GET `/queue`、GET `/history/{prompt_id}` 和 WebSocket 进度接口；具体参数与输出格式以 G08 锁定版本的契约测试为准。[ComfyUI 路由](https://docs.comfy.org/development/comfyui-server/comms_routes)、[消息说明](https://docs.comfy.org/development/comfyui-server/comms_messages)

## 5. 结果未知的消歧策略

| 已知证据 | 下一步 | 可以重新提交吗 |
|---|---|---|
| 本地尚未进入 SUBMITTING 且进程执行路径可确认未发送 | 标记未提交，返回可重试错误 | 可以，沿同 Job 新/恢复 Attempt 策略 |
| 已持久化 prompt_id | 查询同实例队列、历史与本次输出 | 不能直接重提 |
| 无 prompt_id，但有经测试可回读的 request_marker | 枚举同实例队列/历史，验证 marker、请求摘要与实例世代 | 只有取得明确未执行/停止证据后 |
| 找到匹配、完整且校验通过的输出 | 补回执/收集/登记 Artifact | 不需要 |
| 没有记录，历史已清空或实例更换 | 保持 OUTCOME_UNKNOWN，显示证据缺口 | 默认不允许 |
| 运维隔离旧实例并确认不再运行，用户决定重做 | 记录人工处理、潜在既有消耗和新 Attempt | 允许，但不声明此前没有执行 |

request_marker 的存放位置可以是经验证会保留的请求元数据和受控输出前缀；必须验证所选版本在 queue/history/输出中如何保留。不能假设所有 ComfyUI 版本都支持客户端指定 prompt_id，或即使支持就必然具有去重语义。

每个工作流包声明可收集的输出节点和命名规则；可选自定义可靠提交扩展需独立版本化与测试。没有该扩展时，系统采用上表的保守未知结果路径。回查期限建议 10 分钟自动检查，之后进入人工处理并保持记录；超时本身不能转化为“肯定没执行”。

## 6. 执行进度与产物确认

WS 消息只更新阶段/节点进度，断线后重新连接并补查队列/历史。不能收到最后一个节点进度就宣布文件成功。无对应节点执行事件也可能涉及缓存或消息遗漏，因此按实际执行回执及输出验证判断。

执行结束后校验输出归属、类型、文件完整性和预期数量，调用 G06 上传；G06 返回 READY ArtifactManifest 后，控制面才允许 Job.SUCCEEDED。执行成功但上传失败进入 COLLECTING 重试，不再次 POST `/prompt`。

技术 QC 可在收集时先检查可解码、尺寸、帧数和时长，完整规则由 G11 负责。生成无音轨的视频是正常情况，除非本 RenderSpec 明确要求原生音频；最终旁白由 G07/G13 合成。

## 7. 取消与多任务隔离

尚未运行且可准确识别的排队任务使用已验证的队列删除能力。运行中任务的中止 API 可能作用于实例当前执行，首版以“一实例一活跃任务”及独占领取控制风险；中止前重新验证实例世代、当前任务与 attempt 关联。

不能确认当前执行身份时不发送笼统中止命令，进入隔离/人工对账，避免取消别人的任务。取消结束需要收到任务不再排队/运行的证据；若只能杀掉本 Worker 拥有的 ComfyUI 进程，则记录已验证进程身份和实例停止证据。

Worker 重启时默认 DRAINING/RECOVERING，先扫描本地未决日志，对照控制面和 ComfyUI 进程状态；所有实例任务确认后才标 READY。控制面失联时不领取新任务，在途输出落本地持久目录等待补报；磁盘逼近限额则停止后续工作。

## 8. 实现任务

先实现故障可配置的 FakeComfy（受理后断连、清空历史、晚结果、上传失败）和 Worker journal → 单模板真实 API 接入 → 队列/历史/输出回查 → 上传登记 → 中止验证 → 进程重启恢复。真实调用必须经过受控 Worker；前端与 Agent 不能绕过本模块直连 ComfyUI。

## 9. 验收条件

- G10-A1：同 Attempt 重复投递 20 次，只走一次已确认的提交路径；日志和控制面结果一致。
- G10-A2：POST 受理后断网且未保存 prompt_id，能凭已验证 marker 找回；找不回时停在 OUTCOME_UNKNOWN，不盲目重提。
- G10-A3：历史清空/实例换代后查不到任务，不会误判未执行。
- G10-A4：视频生成完成后上传失败，恢复只补上传，ComfyUI 提交次数不增加。
- G10-A5：取消目标 A 时实例当前是 B，系统拒绝错误中止，B 不受影响。
- G10-A6：旧 Worker 晚到结果不能覆盖新选择；重启 Worker 未完成对账不得领取新工作。
- G10-A7：无音轨但合同仅要求视频的镜头可通过收集；路径逃逸和未知输出节点被拒绝。

## 10. 供审核的取舍

采用“能证明才自动重试”的恢复策略，可能有少量任务需要人工处理，但避免把不确定性转化为无声的重复计算。用户显式要求未知任务重做时，新记录必须展示潜在重复消耗并保留原尝试。
