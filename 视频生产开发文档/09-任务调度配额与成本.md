# G09｜任务调度、配额与成本

> 状态：DRAFT_FOR_REVIEW。交付阶段：B1 任务与预算基础，B2 真实节点。前置：G02–G04、G15 身份基础；真实能力来自 G08。交互：G05、G07、G10、G12、G16。

## 1. 目标与边界

把生成任务交给具备相应能力的节点，控制并发、预算和重试。第一版允许只有一个 ComfyUI 实例，但领取、失联、预算和结果协议须支持增加第二个实例。Temporal 管制作流程，调度模块管逻辑渲染任务与节点领取，两者不重复决定同一次 GPU 提交。

## 3. 任务和领取协议

RenderJob 表示用户要求的一份候选；RenderAttempt 表示为完成该任务的一次实际执行尝试。同一技术重试保留 job_id；用户主动“再来一个”创建新 candidate_id/job_id。尝试编号与节点 fence 由服务端生成。

Worker 通过认证内网 API 注册并领取：POST `/internal/workers/register`、POST `/internal/workers/:id/heartbeat`、POST `/internal/render/claim`、POST `/internal/render/attempts/:id/events`。所有事件携带 event_id、job_id、attempt_id、worker_epoch、lease_fence；服务端验证实例、租户工作范围和当前领取。

首版使用 PostgreSQL 任务表作为渲染待办队列。Temporal Task Queue 只分配编排/Activity 执行，不另外复制一份 GPU 待办清单到 Redis。Worker 拉取任务，由调度器返回完整 RenderSpec 引用和短期素材访问权限。

## 4. 调度算法与并发实现

按租户轮转选择可调度队列，在各租户内按优先级和创建时间选择任务，并增加等待时间权重避免长期饥饿。短事务检查预算预留、租户 in_flight 上限、Worker 可用槽和所需能力，以行锁及条件更新原子创建 Attempt/Lease。数据库锁释放后才允许下载素材或访问 ComfyUI。

Alpha 每个 ComfyUI 实例仅允许一个活跃任务，内部队列保持浅层；多 Worker 扩展用多个独立实例。模型缓存亲和性可以作为同优先级排序因素，不得无限跳过长时间等待任务。首版不做自动购买 GPU 或自动扩缩容。

默认 Worker 每 10 秒心跳，租约 60 秒；参数写入 RuntimeProfile 并经实际网络验证。节点心跳和任务进度分开：节点在线但模型卡住，也需要根据 G08 实测阶段超时处理。系统时间用于诊断，领取有效性以服务端数据库时间和递增 fence 判定。

## 5. 失联和接管规则

租约过期后把 Attempt 标成 OUTCOME_UNKNOWN 并停止新派发到相关实例，启动 G10 回查。禁止仅因为心跳丢失就让另一台机器重跑同一任务。

fence 是写入门禁：旧 Worker 不能覆盖当前结果或续租。它不能阻止旧 GPU 继续计算，因此重新派发前必须确认旧执行未提交、已失败/停止，或由运维明确隔离旧实例。无法确认时保持待处理。

旧 Worker 晚到的结果进入对账暂存区；验证任务身份、摘要和时间证据后，可作为历史候选保存。只有当前有效任务状态转换能决定接受结果，不能自动替换用户已选片段。

## 6. 预算账本

`BudgetReservation` 以 operation_id 唯一，记录 tenant、project、run、资源类型、估算版本、预留金额和状态。金额使用带 currency 与 scale 的整数，GPU 秒/Token/存储字节分别记量，不混在一个浮点数里。

制作批次可以有总预算预留，子任务从父预留分配；分配不再重复扣用户可用额度。独立 LLM/配音任务没有父预留时直接预留。账本事件为 RESERVE、ALLOCATE、ADJUST、SETTLE、RELEASE；每条结算操作具唯一 ID，并通过事务检查可用额度。

初始成本 = 供应商报价或实测 GPU 时间估算 + 后处理/存储估算。调度前执行硬准入；长任务按实测时间和执行上限监控。估计不是最终收费，实际超过预留时记录超额、停止安排新工作并告警，不能丢弃真实费用或伪称绝不超支。

已知未执行任务可释放预留；结果未知的外部调用继续占用未决预留，直到回查、供应商账单或经审计的人工处理确认。不得在取消请求发出时直接退回所有额度。

批次结束后结清子任务实际用量，释放未分配和已确定未使用的余额；仍有未知调用时保留对应子预留，账本可以处于待结算状态。长期暂停可释放尚未分配的预算，但恢复必须重新准入，不能继续使用已释放的额度。运维确认无法取得供应商账单时，记录估计结算及其依据，并允许后续差额调整。

MediaJob 复用本模块的预算、租约和服务端 fence 基础，使用单独的 CPU/磁盘能力与并发池，不占用 ComfyUI 的 GPU 槽；G13 定义媒体任务执行日志。LLM/TTS 使用相同预算账本，供应商调用并发按各自 profile 控制。

## 7. 重试分类

| 原因 | 同任务新 Attempt | 修改输入/新候选 |
|---|---|---|
| 确认未提交的连接失败 | 可，最多 2 次技术重试 | 不需要 |
| 提交已发生但回应丢失 | 禁止，先 G10 回查 | 仅在用户了解潜在重复后显式选择 |
| 节点已确认故障且任务终止 | 可，匹配兼容节点 | 不需要 |
| OOM | 可换满足同一执行合同的节点 | 降参数/换模型则新计划 |
| 参数/模型/节点缺失 | 不可盲重试 | 修正 Bundle/计划后重新准入 |
| 用户认为画面不好 | 不属于技术重试 | 新 candidate_id，重新预留预算 |

技术重试总次数默认最多 2 次，加首次最多 3 次 Attempts；与 G04 的 Activity 重试分开，重复 Activity 不自动创建 Attempt。质量自动重做首版默认关闭，后续开启也须有独立次数和金额上限。

## 8. 实现任务与验收

实现任务：任务身份/唯一约束 → 模拟领取 → Worker 注册/租约/fence → 预算账本 → 公平调度 → 重试分类 → 多节点并发测试。

- G09-A1：两个 Worker 同时领取同一任务，只有一个获得当前合法 Lease；单实例没有两个活跃任务。
- G09-A2：租约过期不立即重新生成；旧 fence 提交不能覆盖当前结果。
- G09-A3：用户主动创建相同参数的新候选会得到新 Job，重发原命令不会。
- G09-A4：多个并发任务竞争最后一份额度，不会全部通过预留；父子预留没有重复扣减。
- G09-A5：未知调用的预算不提前释放；重复结算事件只记一次。
- G09-A6：加入第二个实例后业务接口不变；受限租户不会通过增加请求绕过并发额度。
- G09-A7：预算估计偏低时如实记录实际成本，停止新增工作并保留已生成结果。

## 9. 供审核的取舍

首版采用小并发、浅队列和明确预算账本；优先确保重复操作、失联和费用能解释，再优化吞吐。默认不自动按质量反复生成，也不自动降低规格以掩盖执行失败。
